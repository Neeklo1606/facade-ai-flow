# Runbook: база данных PostgreSQL

Адаптер PostgreSQL — [ADR-005](../adr/ADR-005-postgresql-adapter.md). Он нужен рабочему контуру:
сборке `--mode server` на сервере заказчика или на Workers. Публикуемая демонстрация
(`VITE_DATA_SOURCE=demo`) держит данные во вкладке зрителя и базу не использует.

Сервер выбирает адаптер по окружению. Есть `DATABASE_URL` — работает база. Нет — демо-адаптер
в памяти процесса, как раньше.

## 1. Переменные окружения

| Переменная        | Значение                                                             | Если не задана                            |
| ----------------- | -------------------------------------------------------------------- | ----------------------------------------- |
| `DATABASE_URL`    | строка подключения: `postgres://пользователь:пароль@хост:5432/база`  | сервер работает на демо-адаптере в памяти |
| `DATABASE_DRIVER` | `pg` — Node на своём сервере; `neon` — HTTP-драйвер Neon для Workers | `pg`                                      |
| `APP_TIME_ZONE`   | пояс объекта для меток времени, например `Europe/Moscow`             | `Europe/Moscow`                           |

Строка подключения — секрет: только в настройках хостинга или в `.env*.local`, не в репозитории.
Локально без TLS допишите `?sslmode=disable`.

## 2. Первый запуск: схема и начальные данные

Нужен PostgreSQL 16 и пустая база.

```bash
createdb fieldops
export DATABASE_URL="postgres://localhost/fieldops?sslmode=disable"
bun run db:migrate    # схема: все миграции из db/migrations (dbmate)
bun run db:seed       # начальные данные: те же фикстуры, что у демо
```

- `db:migrate` применяет только новые миграции. Повторный запуск безопасен.
- `db:seed` работает только с пустой базой. Если данные уже есть, он откажет и ничего не запишет.
- Миграция создаёт роль `app_user` без права входа. Журналы (`position_changes`,
  `project_decisions`, `project_events`, `sources`, `extractions`) она может только пополнять.
  Приложение подключается владельцем базы; роль — задел на случай, когда подключение
  переведут на неё.

## 3. Запуск сервера на Node

```bash
NITRO_PRESET=node-server bun run build --mode server
DATABASE_URL="postgres://…" DATABASE_DRIVER=pg SESSION_SECRET="…" PORT=3000 node .output/server/index.mjs
```

Проверка: откройте `/projects`, войдите сотрудником, подтвердите позицию и перезапустите
процесс. Подтверждение должно сохраниться.

Проверено 2026-09-20 на локальном PostgreSQL 16. ПТО подтвердила 524 позиции кнопкой
«Подтвердить все проверенные». Запись заняла 73 мс, экран обновился за ~2 с: 18 запросов,
самый долгий — 137 мс. После перезапуска сервера — те же «Проверено 99 %».

## 4. Neon и Workers

1. Создайте базу в Neon. Возьмите строку подключения для прямого подключения, без пула.
2. Примените миграции и сид с любой машины:
   `DATABASE_URL="<строка Neon>" bun run db:migrate && bun run db:seed`.
3. В настройках Workers задайте `DATABASE_URL` и `DATABASE_DRIVER=neon`.
4. Проверьте, как в §3: подтверждение переживает новое развёртывание.

Драйвер Neon написан по документации, но на настоящем Neon ещё не запускался. Первый запуск —
по этому списку. Результат запишите сюда же.

## 5. Новая миграция

Схема описана в контрактах (`src/contracts`), миграции — снимки её изменений.

1. Поменяйте контракт, затем обновите документ схемы: `bun run db:schema`.
2. Создайте миграцию: `bunx dbmate --migrations-dir db/migrations new <что-меняется>`.
3. Перенесите в неё изменения из `docs/db/schema.sql`: `alter table`, `create index`.
   Опубликованную миграцию не правят — только новая.
4. `bun run check:db` сверяет колонки базы после всех миграций с контрактами. Если колонку
   забыли, шаг упадёт.

Откат последней миграции: `bunx dbmate --migrations-dir db/migrations rollback`. Откат начальной
миграции удаляет все таблицы вместе с данными. Перед ним нужна копия из §7.

## 6. Паритет с демо-адаптером

```bash
DATABASE_URL="postgres://localhost/postgres?sslmode=disable" bun run check:db
```

Нужен пользователь с правом `CREATEDB`. Шаг создаёт временную базу `fieldops_check_…`,
применяет миграции, сверяет колонки с контрактами, загружает сид и замеряет реестр материалов.
Затем выполняет одну цепочку операций через демо-адаптер и через базу:

- проверка позиций;
- разделение;
- сопоставление;
- запрос поставщикам;
- решение;
- приёмка с замечанием;
- справочник;
- новый объект.

После каждой записи сравниваются 21 чтение. Отдельно проверяется версия данных. В конце временная
база удаляется. В конвейере (`bun run ci`) строка подключения передаётся через
`CHECK_DATABASE_URL`. Остальные шаги работают без базы.

## 7. Резервная копия и восстановление

```bash
pg_dump --format=custom --file=fieldops-$(date +%F).dump "$DATABASE_URL"
pg_restore --clean --if-exists --dbname="$DATABASE_URL" fieldops-2026-09-20.dump
```

## 9. Ограничения

- **Мост снимка.** Записи и часть чтений загружают все таблицы. На данных демонстрации это
  ~13 мс на чтение и ~18 мс на запись. Когда данных станет на порядки больше, записи
  переводятся на SQL по одной, под паритетным тестом.
- **Записи одного процесса идут по очереди.** Это не больше ~55 записей в секунду на процесс.
  Если между загрузкой и записью данные поменял другой сервер, запись повторяется на свежих
  данных, до трёх раз. После этого сотрудник видит «Данные одновременно меняли другие
  сотрудники».
- **Внешних событий нет.** В режиме базы нет симулятора, поэтому:
  - загруженный документ остаётся в статусе «Загружен»: воркера распознавания нет;
  - ответы поставщиков сами не приходят: приёма ответов нет;
  - отгрузку поставки отмечают вручную.
- **Время.** Метки — время объекта без пояса, в поясе `APP_TIME_ZONE`. В `timestamptz` они
  хранятся как момент UTC с теми же цифрами.
