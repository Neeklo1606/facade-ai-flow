# Handoff Сергею: что подключать после фронтенд-показа

Этот документ не вводит новую серверную реализацию. Актуальные исходники: `src/ports/gas-ops.ts`,
`src/contracts/gas-api.ts`, `src/api/gas-ops-server.ts`, `src/adapters/gas-ops/db-store.ts`.
PostgreSQL, миграции, роли, серверный экспорт и webhooks уже подготовлены; не создавать второй API.
Развёртывание: Dockerfile (`MODE=server`), deploy/Caddyfile, docs/runbook/pilot.md и docs/RUNBOOK.md.

## Существующий путь

MAX/Telegram webhook → проверка секрета/сотрудника → нормализованный эффект диалога →
`callGasMethod` → роль и правила порта → DB-store → PostgreSQL. Веб работает через тот же порт.
В demo вместо DB-store используется localStorage состояния, серверные ответы не подделываются.
Голос: отдельный провайдер транскрипции → черновик полей → сотрудник подтверждает отправку.
AI может предлагать поля и классификацию сметы, не вызывать финансовое подтверждение без человека.

## Что добавлено только для фронтенд-показа

- Ручное назначение использует существующий applySchedule, без нового endpoint.
- Редактирование объекта/демо-статуса: `src/api/gas-demo-workflow.ts`, только demo, общий снимок,
  журнал. В server-режиме кнопка скрыта. Для production нужен метод редактирования, схема
  валидации, серверная роль, DB-маппинг статуса и политика изменения закрытых документов.
- Проект частичных начислений: отдельный ключ браузера по контуру/объекту/версии. Не отправляется
  в backend и не применяется к действующим начислениям. Модель исходников:
  `src/domain/gas-ops/demo-allocation.ts`. Это UX-макет, не утверждённое финансовое правило.

## Следующий контракт после эталонных примеров

1. Раздел сметы: стабильный ID, версия/файл/строка, вид работ, стоимость, подтверждённые материалы,
   единица и общий объём. Одного номера строки для нескольких версий недостаточно.
2. Подтверждение объёма: раздел, бригада, день, доля/объём, автор, статус, причина корректировки.
3. Реестр начислений: ссылка на объём и запись времени, сумма в копейках, остаток, версия правила,
   запрет двойного учёта и отрицательного остатка, поведение при замене сметы/закрытии недели.
4. Источник записи: конкретный MAX/Telegram/web, идентификатор события и диалога; историческое
   значение `bot` не заменять догадкой. Сохранить идемпотентность повторных webhooks.
5. Хранение оригиналов смет с правами и контрольными суммами; текущий браузерный импорт
   сохраняет разбор, а не оригинальный бинарный файл на VPS.
6. Интеграции: состояния «не настроено / настроено / проверено / ошибка», последнее успешное
   событие, безопасная причина отказа. Не выдавать наличие env-переменной за health-check.

## Приёмка backend

Пустая компания → роли → объект/бригада → ручной/Excel график → настоящая смета → реальное
сообщение каждого канала → ручная проверка → неизменный объект/дата → Excel из базы.
Проверить повтор сообщения, отказ сети, чужую роль, конфликт версии, закрытый период и
сверку копеек/минут с утверждёнными 2–3 примерами. Базовый пример времени: 08:30–11:40 = 190 минут
до вычета перерыва. Эталоны частичных объёмов и СМР/опрессовки утверждает заказчик.
