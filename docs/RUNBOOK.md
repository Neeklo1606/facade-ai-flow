# Runbook: развёртывание, откат, восстановление

Боевой адрес: **https://facade-ai-flow.lovable.app** — демонстрация, закрытая ключом в ссылке.
Хостинг — Lovable поверх Cloudflare, сборка — Vite + Nitro, серверная часть работает
(SSR, выгрузка в Excel, приём ошибок).

**Перед выпуском** пройдите чек-лист [RELEASE.md](RELEASE.md): что проверить до показа
и до запуска у заказчика, и что останавливает выпуск.

## 1. Что где лежит

| Что                   | Где                                                                                                      |
| --------------------- | -------------------------------------------------------------------------------------------------------- |
| Исходный код          | GitHub, `Neeklo1606/facade-ai-flow`, ветка `main`                                                        |
| Публикация            | lovable.dev, кнопка **Publish → Update**; Lovable собирает из `main`                                     |
| Резервные копии веток | `<репозиторий>/.bundles/*.bundle` (`git clone <файл>.bundle`)                                            |
| Данные демонстрации   | в браузере зрителя: `sessionStorage` вкладки (ADR-004), на сервере ничего не хранится                    |
| База рабочего контура | PostgreSQL 16 по `DATABASE_URL` (ADR-005); порядок работы — [`runbook/database.md`](runbook/database.md) |
| Логи                  | Lovable → логи проекта; там же видны сообщения `[client-error]`                                          |

## 3. Развёртывание

1. Изменения влиты в `main` (после независимого ревью; BLOCKER и HIGH блокируют мерж).
2. lovable.dev → **Publish → Update**. Сборка идёт 1–3 минуты.
3. Проверить боевой адрес по чек-листу из §6.
4. Если менялся ключ доступа — разослать новую ссылку `https://facade-ai-flow.lovable.app/?k=<ключ>`.

Локальная проверка боевой сборки перед публикацией:

```bash
bun install
bunx tsc --noEmit -p tsconfig.json
bun lint
NITRO_PRESET=node-server bun run build                      # публикуемый контур (demo)
NITRO_PRESET=node-server bun run build --mode server        # рабочий контур, если нужен
DEMO_ACCESS_KEY=локальный-ключ PORT=4620 node .output/server/index.mjs
# http://localhost:4620/?k=локальный-ключ
```

## 4. Откат

Проверенный путь — откат кода и повторная публикация:

```bash
git revert <коммит>      # или git revert <старый>..<новый> для серии
git push origin main
# затем Publish → Update в lovable.dev
```

Если в Lovable доступна история публикаций — можно вернуться к предыдущей версии её средствами;
это быстрее, но репозиторий останется впереди, и следующая публикация вернёт проблему.
Поэтому после отката средствами Lovable всё равно откатите код.

Историю не переписываем: `git push --force` в этом репозитории запрещён — Lovable синхронизируется
с веткой и потеряет состояние.

## 5. Восстановление

| Что случилось                       | Что делать                                                                                                                                                                                                       |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ветка потеряна локально             | `git clone .bundles/<имя>.bundle восстановленное` — в бандлах лежат полные ветки                                                                                                                                 |
| Демо-данные «испортились» на показе | в меню слева внизу «Сбросить демо-данные» → подтвердить; вернётся эталонный набор                                                                                                                                |
| Зритель видит чужие изменения       | этого не бывает: состояние живёт в его вкладке. Новая вкладка = эталон                                                                                                                                           |
| Репозиторий недоступен              | последний бандл + `.output` собранной версии; восстановить репозиторий из бандла и запушить                                                                                                                      |
| Подпись сессий нужно сменить        | задать или сменить `SESSION_SECRET` на хостинге: все cookie `fieldops_session` станут недействительны, вкладки войдут заново за свою персону                                                                     |
| Ключ утёк                           | сменить `DEMO_ACCESS_KEY` в настройках хостинга и разослать новую ссылку; старые cookie перестанут подходить. Если ключ задавался через `VITE_DEMO_ACCESS_KEY`, нужна ещё и пересборка: значение зашито в сборку |

## 6. Чек-лист после публикации

```bash
KEY=<ключ>; URL=https://facade-ai-flow.lovable.app; JAR=$(mktemp)
curl -s -o /dev/null -w "%{http_code}\n" $URL/                          # 401 — шлюз работает
curl -s -o /dev/null -w "%{http_code}\n" -c $JAR --get --data-urlencode "k=$KEY" $URL/
                                                                         # 302 — ключ принят, cookie в банке
curl -s -o /dev/null -w "%{http_code}\n" -b $JAR $URL/                  # 200 — приложение
curl -s -D- -o /dev/null -b $JAR $URL/ | grep -i x-robots-tag            # noindex
curl -s $URL/robots.txt                                                  # Disallow: /
curl -s -o /dev/null -w "%{content_type}\n" -b $JAR $URL/api/export/projects
                                                                         # spreadsheetml — выгрузка жива
curl -s -o /dev/null -w "%{http_code}\n" -b $JAR $URL/design-system      # 404 — витрины в публикации нет
```

Банка cookie (`-c` и `-b`) вместо ручной строки: ключ с кириллицей или пробелом хранится
в cookie процентно-закодированным, и собранная руками строка `fieldops_demo=$KEY` для такого
ключа не подойдёт. По той же причине ключ передаётся через `--data-urlencode`, а не подставляется
в адрес: на кириллическом ключе curl отказывается разбирать адрес, а на ключе с пробелом — сервер
отвечает 400, и проверка падает на исправном сайте.

Руками: открыть ссылку с ключом на телефоне в мобильной сети, пройти сценарий из
[DEMO.md](DEMO.md), отправить ссылку себе в мессенджер и посмотреть превью.

## 7. Наблюдаемость

- **Ошибки фронтенда.** Необработанные ошибки, отклонённые промисы и падения границы ошибок
  уходят POST-запросом на `/api/client-error` и пишутся в лог хостинга с префиксом `[client-error]`.
  Ищите по этому префиксу. За сессию отправляется не больше двадцати сообщений, повторы одного
  и того же текста не дублируются. Наружу не уходит ничего, кроме текста ошибки, адреса экрана
  и строки браузера.
- **Доступность адреса.** Workflow лежит в `docs/ops/uptime.yml` и **начинает работать только
  после копирования в `.github/workflows/uptime.yml`** (токен, которым пушится ветка, не имеет
  права `workflow`, поэтому файл не попадает туда автоматически; проще всего скопировать через
  веб-интерфейс GitHub: Add file → Create new file). Раз в 15 минут проверяет
  `robots.txt`, главную страницу и выгрузку в Excel. При сбое запуск падает, и GitHub присылает
  письмо. Настройка: переменная репозитория `DEMO_URL` (если адрес сменится) и секрет
  `DEMO_ACCESS_KEY` (Settings → Secrets and variables → Actions). Без секрета проверка мягче:
  страница считается живой при 200 или 401.

- **Проводка и статистика показа (ADR-010).** Чистая вкладка начинается с выбора роли; дальше
  панель проводки справа внизу ведёт по сценарию роли. Статистика вкладки — скрытый экран
  `/demo-stats`: шаги, время по экранам, действия, ошибки, точка выхода. Он показывает только
  ту вкладку, в которой открыт, поэтому смотреть его надо на машине, где шёл показ.
- **«Непонятно на этом экране».** Строка JSON с `"channel":"feedback"` в журнале хостинга:
  экран, шаг сценария, персона, текст. Ищется рядом с ошибками фронтенда.

## 8. Частые проблемы

| Симптом                                                   | Причина                                                          | Что делать                                                                                                |
| --------------------------------------------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| Везде экран «Демонстрация открывается по ссылке с ключом» | сменился или пропал `DEMO_ACCESS_KEY`                            | проверить переменную на хостинге, открыть ссылку с актуальным ключом                                      |
| Белый экран, в логе `[client-error]`                      | ошибка фронтенда                                                 | найти сообщение в логе, воспроизвести локально на той же сборке, откатить публикацию, если ломается показ |
| Выгрузка в Excel не скачивается                           | блокировщик или ответ не 200                                     | проверить `curl` из §6; в Safari — разрешить загрузки; в логе смотреть ответ `/api/export/projects`       |
| Цифры «не те», что были вчера                             | у зрителя в вкладке своё состояние демо                          | «Сбросить демо-данные» либо новая вкладка                                                                 |
| Показ идёт в двух вкладках, данные разные                 | так устроен демо-контур: состояние на вкладку (ADR-004)          | вести показ в одной вкладке                                                                               |
| Первый экран грузится долго на мобильной сети             | в демо-режиме данные строятся в браузере после загрузки скриптов | предупредить зрителя, открыть адрес заранее; ускорение — отдельная задача (SSR данных в демо-контуре)     |
| Шрифт не тот                                              | Google Fonts заблокирован сетью зрителя                          | системный шрифт подставляется автоматически, показ можно продолжать                                       |
| В поиске появилась демонстрация                           | публикация без `DEMO_ACCESS_KEY`                                 | задать ключ, проверить `robots.txt` и заголовок `X-Robots-Tag: noindex`                                   |

## 9. Проверки и конвейер (ADR-013)

Весь конвейер локально — одна команда. Она печатает код возврата каждого шага и останавливается
на первом падении:

```bash
bun run ci
```

| Шаг        | Команда                                  | Что ловит                                                                                                                                                                       |
| ---------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Типы       | `bun run typecheck`                      | ошибки типов в коде и в тестах                                                                                                                                                  |
| Линтер     | `bun run lint`                           | границы слоёв: данные фикстур вне `adapters/fixtures`, `adapters/demo` и `adapters/db`, формулы в экранах                                                                       |
| Тесты      | `bun run test`                           | правила домена с граничными случаями; согласованность цифр между экранами; негативные сценарии в адаптере                                                                       |
| Фикстуры   | `bun run check:fixtures`                 | данные против схемы, точность `numeric`                                                                                                                                         |
| PostgreSQL | `bun run check:db`                       | миграции, колонки против контрактов, паритет адаптера базы с демо, версия данных (ADR-005)                                                                                      |
| Сборка     | `NITRO_PRESET=node-server bun run build` | сборка демо на node-сервере для следующих шагов                                                                                                                                 |
| Бандл      | `bun run check:bundle`                   | gzip клиента против порогов `scripts/bundle-budget.json`                                                                                                                        |
| Сквозные   | `bun run test:e2e`                       | сценарий каждой роли и сценарий показа, одна цифра на всех экранах, честность, статусы, доступ без прав, одно оранжевое пятно, капс, axe, консоль, мобильная версия; 1440 и 375 |
| Lighthouse | `bun run lighthouse`                     | доступность ≥ 95, практики ≥ 90, производительность ≥ 70 на трёх экранах                                                                                                        |

Обход продукта — вне конвейера, ~35 минут: `bun run walkthrough` нажимает каждый элемент каждого
экрана за пять ролей и проверяет мобильную версию на 375, 390 и 430; `bun run walkthrough:report`
собирает `docs/state/walkthrough.md` и снимки экранов (ADR-015).

Шагу PostgreSQL нужен сервер PostgreSQL 16: `CHECK_DATABASE_URL=postgres://localhost/postgres bun run ci`.
Локально сквозные тесты могут взять уже установленный Chromium: `PW_CHROMIUM=<путь> bun run ci`.
Иначе один раз: `bunx playwright install chromium`.

В GitHub тот же порядок шагов — `.github/workflows/ci.yml`, проверка называется `checks`.
**Запрет слияния включает владелец репозитория:**

1. Откройте Settings → Branches.
2. В правиле для `main` включите «Require status checks to pass before merging».
3. Выберите проверку `checks`.

Без этой настройки конвейер показывает падение, но слияние не блокирует.

Порог бандла поднимают правкой `scripts/bundle-budget.json` с объяснением в коммите.
Пороги Lighthouse не снижают: экран ниже цели — задача в `TASKS.md`.
