# Данные газового заказчика: где лежат и куда попадают

Версия 1.0 от 22.10.2026, шаг L0. База ff93d98. Вход для ADR-047 в L1.
Сами данные здесь не приводятся: «итог недели заказчика», а не число.

## 0. Главное

1. **Репозиторий публичный** (`gh repo view`: PUBLIC). Всё, что ниже отмечено «в git»,
   уже доступно любому на GitHub, независимо от того, что попадает в сборку. Перенос данных
   в серверный модуль (01_SPEC 6.2) закрывает сайт, но не репозиторий.
2. **Название заказчика** лежит в главном куске клиентской сборки `index-*.js`: его скачивает
   любой посетитель любой страницы, включая корень.
3. **Все 21 населённый пункт из файла заказчика и итог недели** лежат в куске `gas-ops-*.js`,
   который грузится на /gas.
4. В HTML первого ответа сервера (SSR) для `/`, `/gas`, `/gas/reports` ни названия,
   ни населённых пунктов, ни итога нет: экраны /gas рисуются на клиенте.
5. Объект показа ОБ-200 вымышленный, но стоит в реальном населённом пункте из файла заказчика.

Проверка: `bun run build` (демо), поиск строк по 265 файлам `.output/public/**`
(`.js`, `.html`, `.css`, `.json`) и по HTML ответа локального сервера. Список строк
для поиска собран из `fact-report.lite.json` во временный файл вне репозитория.

## 3. Кто зависит и что сломается при переносе

- **Расчёт.** `src/domain/gas-ops/*` данных не импортирует, работает с тем, что передали.
  Перенос набора его не трогает.
- **Состояние /gas.** `src/adapters/gas-ops/state.ts` строит стартовое состояние из
  `gas-ops-seed.ts` прямо в браузере и хранит изменения показа локально. Публичный набор
  подключается заменой импорта; личный контур требует отдачи набора с сервера по куке
  и загрузки до первого рендера /gas.
- **Сверка с файлом заказчика.** `src/api/gas-report.ts` сравнивает неделю с `factReport`.
  В публичном контуре блок скрывается (01_SPEC 6.4), в личном набор приходит с сервера.
- **Показ gas-week.** ОБ-200 и его 14 700 ₽, 2,50 ч, 5 880 ₽/ч живут в `gas-ops-seed.ts`.
  В публичном наборе ОБ-200 нужно перенести в вымышленный населённый пункт, цифры сохранить.
- **Тесты, которые проверяют цифры файла заказчика:** `gas-ops-calc`, `gas-ops-report`
  (итог недели против дерева), `gas-ops-contour`, `gas-show-defects`, `e2e/gas-report-state.ts`,
  `scripts/check-gas-export.ts`. По L1 они остаются и работают на наборе заказчика.
- **Бюджет сборки.** Набор заказчика 60 КБ сырых (около 4 КБ gzip). Публичный набор того же
  размера заменит его, общий размер почти не изменится.

## 4. Что из этого следует для L1

1. Публичный набор строится скриптом и лежит в `src/data/mock/public/`. Клиентский код
   импортирует только его и бренд «Демо-подрядчик».
2. Набор заказчика импортируется только серверным модулем и тестами. Проверка
   `check:public-bundle` ищет в сборке название, 21 населённый пункт и итог недели.
3. **Репозиторий.** Пока он публичный, данные заказчика из git видны на GitHub. Варианты
   для владельца: а) сделать репозиторий приватным (до этого проверить, что синхронизация
   Lovable с приватным репозиторием не рвётся); б) вынести набор заказчика из git в переменную окружения хостинга или файл,
   который кладётся при публикации. Без решения перенос в серверный модуль закрывает
   только сайт. Это вопрос владельцу в PLAN.md, шаг L1 он не блокирует.
4. Список запретов в `scripts/gas-shots.ts` (фамилии) заменяется проверкой по хешам
   или переезжает в серверный модуль вместе с набором.
