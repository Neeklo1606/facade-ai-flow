# ADR-010. Проводка по сценарию, подсказки, телеметрия сессии и обратная связь

- **Статус:** принято
- **Дата:** 2026-09-19
- **Задача:** Q2 очереди «Проводка по сценарию и телеметрия»
- **Связано:** [ADR-004](ADR-004-demo-adapter-in-browser.md) (состояние во вкладке),
  [ADR-008](ADR-008-demo-personas-and-honest-limits.md) (персоны и честные границы),
  [аудит Q1](../audit/Q1-completeness-gap.md)

## Контекст

Демонстрацию сейчас проводит ведущий по сценарию `docs/DEMO.md`. Посторонний человек, открывший
ссылку сам, не знает, с чего начать, а владелец не видит, где этот человек остановился. Нужны:
выбор роли при первом входе, проводка по сценарию роли, подсказка на каждом экране, телеметрия
сессии и кнопка «Непонятно на этом экране».

## Решения

1. **Пять ролей на экране выбора:** руководитель проекта, снабжение, ПТО, прораб, директор.
   - ПТО — существующий сотрудник Волкова М. С., роль `pto` в модели есть.
   - **Директора в модели не было.** В перечисление `employeeRole` добавляется значение
     `director`, в фикстуры — сотрудник Беляев В. Н., генеральный директор. Данные демонстрации
     вымышлены целиком (ADR-008), это ещё одна персона того же рода.
   - Откат: убрать одно значение перечисления и одну запись фикстур.

2. **Экран выбора роли** показывается один раз за вкладку, поверх первого экрана.
   Выбор хранится там же, где персона, — в `sessionStorage` вкладки (ADR-004). Под выбором две
   строки о том, что это за система. Роль задаёт персону, стартовый экран и сценарий проводки.

3. **Проводка — декларативные сценарии по ролям** в `src/lib/guide/scenarios.ts`: шаг, экран,
   элемент для подсветки (атрибут `data-tour`), условие засчитывания и переход на нужный экран.
   - **Шаг засчитывается по факту**: по переходу на экран или по действию, которое действительно
     изменило данные. Действия берутся из общего кеша мутаций (`MutationCache`) по подписи `meta.action`,
     которую получает каждая мутация. Новых портов для этого не нужно.
   - Кнопка «Дальше» до выполнения шага недоступна и объясняет, чего ждёт шаг. «Пропустить»
     переводит к следующему шагу с отметкой «пропущен».
   - **Подсветка — тонкая линия, а не пятно.** Правило EMBER «одно оранжевое пятно» касается
     залитых акцентов: кнопок, значков, свечения. Контур подсветки — линия толщиной 1,5 px вокруг
     элемента, которую ведёт проводка, и только пока шаг не выполнен. Заливок и второго акцента она
     не добавляет. Проверяется скриптом правил EMBER.
   - Тексты шагов говорят только о том, что система действительно делает. Где звено имитируется —
     ответы поставщиков, — шаг говорит об этом прямо. Приёмки поставки пока нет, и в сценарий
     снабжения она не входит; появится с задачей Q4.

4. **Подсказка экрана** — иконка вопроса в шапке у заголовка. По ней открываются три предложения
   из общего словаря экранов `src/lib/guide/screens.ts`: что это за экран, на какой вопрос он
   отвечает, что делать дальше. Тот же словарь даёт названия экранов телеметрии и обратной связи.

5. **Телеметрия — журнал вкладки** в `sessionStorage`. Пишутся:
   - открытие экрана и время на нём;
   - главные действия — мутации с подписью `meta.action`;
   - завершённые и пропущенные шаги;
   - ошибки действий;
   - обратная связь;
   - точка выхода — экран, на котором вкладку закрыли или увели.

   Журнал ограничен 500 записями — старые вытесняются. Наружу он не уходит: это статистика
   сессии для того, кто сидит за экраном. Скрытый экран `/demo-stats`, которого нет в меню,
   показывает журнал текущей вкладки.

6. **Обратная связь** — кнопка «Непонятно на этом экране» в правом нижнем углу рядом с проводкой.
   Поле в одну строку, отправка на серверный маршрут `/api/feedback`. Сервер пишет строку JSON
   с `"channel":"feedback"` в журнал хостинга: экран, шаг проводки, персона, текст до 300 символов.
   Та же запись попадает в телеметрию сессии.

## Что не делаем

- Не отправляем телеметрию на сервер: владелец видит статистику на экране той вкладки, где шёл
  показ. Сбор со всех посетителей — отдельное решение о хранилище и о согласии посетителей.
- Не храним роль между вкладками: новая вкладка — новый выбор, как и новое состояние демо (ADR-004).

## Последствия

- Скрипты проверки, которые открывают приложение в чистой вкладке, должны отметить выбор роли
  сделанным, иначе первым будет экран выбора. Для этого есть ключ `neeklo-fieldops-role-chosen`.
- Появление новой роли `director` расширяет все словари по ролям; TypeScript проверяет их полноту.
