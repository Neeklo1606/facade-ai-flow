# ADR-057. Снабжение v1: заявка, предложения, заказ, приёмка

Дата: 30.10.2026. Статус: принято (S5).
Основание: docs/design/GAIKA_SERVICE_V1_PROMPTS.md, разделы 1.1, 1.3, 1.4, 2.4 и S5; ADR-038,
ADR-053, ADR-055, ADR-056.

## Task Brief

Цель: модуль 2 «Снабжение» проходит путь заявки:

1. прораб создаёт заявку;
2. снабженец запрашивает и сравнивает предложения;
3. человек заказывает сам, система отмечает «заказано», затем «в пути»;
4. прораб принимает поставку, в том числе с расхождением;
5. принятые материалы с сертификатами видны ПТО.

Класс T2: демо-данные и порт, без рабочей базы, без писем поставщикам и без ключей моделей.

Расхождения с документом владельца:

- Модуль строится в оболочке `/gas`, а не возвращается из флага `legacy_modules`. Причина: прежние
  закупки (ADR-025, ADR-038) завязаны на объекты ГАЙКИ и их спецификации, а объекты сервиса v1
  живут в контуре `/gas`, данные заказчика загружает его маршрут (ADR-047). Прежний код
  остаётся за флагом без изменений, его проверки не трогаются. Из него взят текст запроса цены
  (`DEFAULT_RFQ_TEMPLATE`), формулировки переписаны под заявку.
- Номенклатуры у заказчика нет. Для показа в списке есть демо-номенклатура: позиции газового
  монтажа с единицами, без цен, с меткой «Демо». Цены появляются только из введённых
  предложений.
- В разобранной смете (ADR-053) есть только итоги, позиций материалов нет. Поэтому лимит по смете
  задаётся строками `MaterialLimit` с источником. В демо-наборе две строки на одном демо-объекте
  с меткой «Демо». Нет строки — экран пишет «Лимита по смете нет», а не ноль.
- Голос: распознавание речи для этого контура не подключено (ADR-049). Кнопка микрофона
  показывается, только если браузер сам умеет распознавать речь (Web Speech API). Иначе её нет
  и ввод текстом. Разбор текста одинаковый для обоих путей.
- Роль ПТО появляется сейчас с одним экраном «Материалы». «Документы» ПТО строятся на S6.
- У прораба, как у бригадира, нет меню и плавающей панели: свой интерфейс телефона «Сегодня
  прораба» с голосом 56 на экране.

## Решение

### 1. Данные (`src/domain/gas-ops/supply.ts`)

- `SupplyRequest`:
  - номер «ЗК-00001», объект, строки `{itemId, qty}`;
  - нужно к дате, приоритет, фото (имена файлов), автор;
  - `clientKey`, статус, причина отклонения;
  - выбранное предложение, дата «в пути», история статусов.
- Статусы: `new → in-work → waiting-offers → ordered → in-transit → partial | delivered → closed`.
  Отклонить с причиной можно из любого незакрытого статуса до «заказано».
  Переходы проверяет `canMove`, а не экран.
- `Supplier`: название, ИНН, контакты, категории, источник.
- `Offer`:
  - поставщик, цена за единицу по строкам в копейках;
  - срок в днях, доставка, условия, имя файла;
  - кто ввёл.
- `Receipt` (приёмка):
  - факт по строкам, расхождение словами, фото накладной;
  - сертификаты и паспорта по строкам (имена файлов);
  - итог «принято» или «принято с расхождением».
- `MaterialLimit`: объект, позиция, количество по смете, источник.

### 2. Правила

- Разбор текста заявки `parseRequestText`:
  - ищет позицию номенклатуры по названию и синонимам, количество и единицу;
  - не угадывает: нет совпадения — строка без позиции и с низкой уверенностью;
  - нет количества — строка без количества.

  Прораб подтверждает или правит каждую строку (правило 1, инвариант 6).
- Срок «к пятнице», «завтра», «до 05.11» разбирается от «сегодня» направления.
- Сверка с лимитом `limitCheck`:
  - заказано — сумма строк той же позиции и объекта в заявках со статусом «заказано» и дальше;
  - в заявке — эта строка;
  - превышение — сколько выходит за лимит;
  - нет лимита — `null`.
- Сравнение `compareOffers`:
  - итог по каждому предложению — сумма строк плюс доставка;
  - лучшая цена и лучший срок отмечаются отдельно;
  - предложение без цены хоть по одной строке получает итог `null` и не может быть лучшим.
- Приёмка `receiptOf`:
  - факт меньше заказанного по любой строке — статус «доставлено частично»;
  - иначе «доставлено»;
  - любое расхождение без описания — ошибка, принять с расхождением молча нельзя;
  - вторая приёмка дополняет частичную.
- Просрочено к дате: «нужно к» раньше сегодня, а заявка ещё не доставлена и не закрыта.
- Повтор создания с тем же `clientKey` возвращает ту же заявку (инвариант 4).
- Заказ поставщику система не делает (инвариант 9). «Отметить заказано» ставит человек после
  своего заказа. «Запросить предложения» даёт файл xlsx и текст для копирования, писем нет.

### 3. Права (демо-адаптер, как будущий сервер)

- Создать заявку: прораб (только свои объекты), снабженец, администратор.
- Решения по заявке (в работу, предложения, выбор, заказано, в пути, отклонить): снабженец
  и администратор.
- Принять поставку: прораб своих объектов, снабженец, администратор.
- Руководитель и ПТО только читают. Прораб не получает цен предложений: выборка прораба
  `siteSnapshot` перечисляет поля явно.

### 4. Экраны

- Прораб, «Сегодня прораба» (`/gas/site`): «Новая заявка» голосом или текстом, черновик строк,
  «Мои заявки» со статусом и ожидаемой датой, приёмка доставки.
- Снабженец:
  - «Заявки» (`/gas/supply`): показатели, таблица по сроку и приоритету, фильтры;
  - деталь заявки (`/gas/supply/$requestId`);
  - «Поставщики» (`/gas/suppliers`);
  - «Поставки» (`/gas/deliveries`).
- Руководитель:
  - «Снабжение» (`/gas/supply-overview`): суммы заказов, просрочки, превышения сметы;
  - блок «Снабжение» в «Неделе».
- ПТО: «Материалы» (`/gas/materials`) — принятые материалы с сертификатами по объектам.

## Последствия

- Версия снимка вкладки 5 → 6: поле `supply`.
- Роли `prorab`, `supply`, `pto`: меню, стартовые экраны и переключатель ролей.
- Отдельный порт `GasSupplyPort` поверх того же состояния: сброс показа возвращает и снабжение.
- Серверный маршрут `/api/gas/rfq` собирает файл запроса так же, как недельный отчёт.
