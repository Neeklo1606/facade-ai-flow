# ADR-005. Адаптер PostgreSQL

- **Статус:** принято (восстановлено)
- **Дата:** 2026-09-20; первая редакция — 2026-09-16, утеряна
- **Задача:** Q7 очереди «Адаптер PostgreSQL»
- **Связано:** [ADR-001](ADR-001-data-layer.md) (порты, контракты, `uuid`-ключи),
  [ADR-004](ADR-004-demo-adapter-in-browser.md) (демо-адаптер), [ADR-012](ADR-012-roles-and-access.md),
  [ADR-013](ADR-013-tests-and-pipeline.md), `TASKS.md` — «Утраченный ADR-005»

## Почему восстановлено

Первая редакция лежала в ветке `phase-3-db` вместе с реализацией. Ветку не запушили, и
2026-09-17 она пропала при очистке сессионного каталога. Уцелели решения из записей прошлой
фазы — они повторены здесь как пп. 1 и 3. Остальное решено заново под текущую модель: права,
поставки, нормализация появились после первой редакции.

## Контекст

- **Сервер работает на демо-адаптере в памяти.** Данные теряются при перезапуске, на нескольких
  экземплярах расходятся.
- **Демонстрация и заказчик.** Демонстрация развёрнута на Cloudflare Workers. У заказчика
  продукт должен работать на своём сервере с PostgreSQL 16.
- **Контракты задают схему.** `docs/db/schema.sql` генерируется из `src/contracts`. Ключи —
  `uuid` (ADR-001, п. 3), а фикстуры, адреса экранов и персоны используют читаемые ключи
  (`p-korona`, `e-sokolov`).
- **Правила домена живут в демо-адаптере и `domain/`.** Переписать их на SQL целиком значит
  завести вторую реализацию, которая разойдётся с первой.

## Решения

1. **Драйвер выбирается окружением.**
   - `DATABASE_DRIVER=pg` — `pg` (node-postgres) для Node на сервере заказчика.
   - `DATABASE_DRIVER=neon` — `@neondatabase/serverless` по HTTP для Workers.

   Строку подключения даёт `DATABASE_URL`. О Neon знает только `src/adapters/db/driver.ts`.
   Выше драйвера — один интерфейс: запрос с параметрами и атомарный пакет запросов.
   Интерактивных транзакций нет: HTTP-драйвер Neon их не держит.

2. **Схема — из контрактов.**
   - DDL генерирует `bun run db:schema` из `src/contracts`.
   - Индексы — из метаданных таблиц. Тест требует индекс на каждом внешнем ключе и индексы
     полей, по которым фильтруют реестры.
   - Проверка — на локальном PostgreSQL 16.

3. **Миграции — dbmate, одна команда.**
   - `bun run db:migrate` применяет `db/migrations/*.sql`.
   - `bun run db:seed` загружает начальные данные из тех же фикстур, что у демо.
   - Порядок — `docs/runbook/database.md`.

   dbmate ставится пакетом npm: бинарник под платформу входит в пакет и не скачивается
   при запуске.

4. **Ключи.** В базе — `uuid`, как требует ADR-001. Читаемый ключ фикстуры превращается
   в детерминированный `uuid`. Таблица соответствий собирается из самих фикстур при старте
   адаптера, в базе её нет. Новые записи получают `uuid` сразу.
   - Снаружи адаптер отдаёт те же ключи, что демо. Поэтому адреса экранов, персоны
     и сессии ADR-012 работают без изменений.
   - Паритетный тест сравнивает ответы двух адаптеров напрямую.

5. **Что считает база.** Пейджинг, счётчики и агрегаты реестров — запросами SQL:
   - список позиций страницами;
   - фасеты и выделение позиций материалов;
   - реестр объектов со сводкой одним запросом;
   - карточка объекта.

   Остальные чтения и все записи идут через мост снимка:
   1. Таблицы загружаются.
   2. Тот же сборщик видов, что у фикстур, строит состояние.
   3. Выполняется то же действие демо-адаптера — правила не дублируются.
   4. Разница по первичным ключам пишется одним атомарным пакетом.

   Пакет начинается проверкой версии данных `app_state.version`. Если между загрузкой и записью
   кто-то успел записать, пакет откатывается, и действие повторяется на свежих данных,
   до трёх раз. Потерянных обновлений нет.

6. **Время.** Метки в данных — местное время объекта без пояса (`domain/time.ts`).
   - В `timestamptz` они пишутся как момент UTC с теми же цифрами: `AT TIME ZONE 'UTC'`.
   - Читаются обратно без сдвига.
   - Пояс сеанса базы на результат не влияет.

7. **Паритет — условие готовности.** `bun run check:db` выполняет одинаковую цепочку операций
   через демо-адаптер и через базу и сравнивает ответы:
   - проверка позиций;
   - передача;
   - запрос;
   - решение;
   - приёмка;
   - сопоставление;
   - справочник.

   Сгенерированные ключи и время создания сравниваются по месту, а не по значению.
   Шаг входит в конвейер ADR-013. В GitHub Actions база — сервис PostgreSQL 16.

## Дополнение 2026-09-20: решения, принятые при реализации

8. **Порядок строк хранится.** Действия демо вставляют записи в начало списков (новый запрос,
   поставка, решение) и в середину (часть разделённой позиции). От порядка зависят ответы портов:
   страницы позиций, порядок листов и разделов в счётчиках. Поэтому у каждой таблицы есть служебная
   колонка `row_order double precision`, как `created_at`: генератор схемы добавляет её сам,
   в API она не отдаётся.
   - Загрузка идёт `order by row_order, id`.
   - Новая строка получает значение между соседями. Если места между соседями нет или порядок
     старых строк поменялся, таблица нумеруется заново.
   - Сортировка по `created_at` не подходит: вставка в начало и в середину её ломает.

9. **Ключи вне `uuid`-колонок.** Две колонки хранят ключи строк без внешнего ключа:
   `extractions.applied_id` (текст) и `supplier_profiles.categories` (`text[]`). В контрактах
   они помечены признаком `holdsIds`, и кодек ключей переводит их так же, как `uuid`-колонки.
   Таблицу соответствий кодек строит из ключей фикстур. Поэтому к модулям, которым можно
   импортировать фикстуры (ADR-013, п. 5), добавляется `src/adapters/db`.

10. **Ключи, которые создают действия.**
    - В режиме базы `liveId` выдаёт `uuid`.
    - Три ключа собирались из ключа родителя: строка запроса `${запрос}-l1`, строка поставки
      и строка предложения. Они получают собственный ключ через `liveId`.
    - Номер запроса считается как «наибольший номер года + 1», а не по признаку `-live-` в ключе.
      Для демо номера те же: первый новый запрос — `З-2026/326`.

11. **Производные поля хранятся согласованными.** `purchase` и `delivered_qty` позиции
    пересчитываются при сборке из принятых поставок (`withDeliveries`). В базу пишется уже
    пересчитанное значение: и сид, и мост записывают `snapshotTables(buildSnapshot(…))`. Тест
    неподвижной точки гарантирует, что повторная сборка их не меняет. Поэтому фильтр по этапу
    закупки в SQL даёт то же, что правило в памяти.

12. **Часы и симулятор в режиме базы.**
    - Время — настоящее, по часам на стене в поясе объекта: `APP_TIME_ZONE`, по умолчанию
      `Europe/Moscow`. Часы демо отсчитывают от «сегодня» фикстур с момента запуска процесса,
      и после перезапуска новые записи получали бы метки раньше уже записанных.
    - Симулятора нет, отложенные события не заводятся. Распознавание загруженного документа
      и ответы поставщиков в режиме базы сами не приходят: воркера распознавания и приёма ответов
      пока нет. Это ограничение записано в runbook.
    - Паритетный тест подставляет обоим адаптерам одинаковые пошаговые часы.

13. **Паритетный тест не трогает рабочие базы.** `check:db` по `DATABASE_URL` создаёт отдельную
    временную базу, применяет миграции, загружает сид, сравнивает и удаляет базу. Ему нужно право
    `CREATEDB`. Сверка колонок базы с контрактами входит в тот же шаг.

14. **Записи одного процесса идут по очереди.** Проверка в `check:db` нашла: четыре одновременные
    записи с тремя попытками без паузы теряют последнюю — она проигрывает все три раза.
    - Внутри процесса записи выполняются по одной. Друг другу они не мешают, повтор не нужен.
    - Повтор с паузой со случайной долей остаётся для записей с разных серверов.
    - Цена: не больше ~30 записей в секунду на процесс при времени записи ~30 мс. Для объёма
      демонстрации и первого заказчика этого достаточно. Когда перестанет хватать — записи
      переводятся на SQL (см. «Последствия»).

## Последствия

- **Сервер выбирает адаптер по окружению.** Есть `DATABASE_URL` — база, нет — демо в памяти,
  как раньше. Контур демонстрации в браузере не меняется.
- **Мост снимка загружает все таблицы на каждое действие.** На данных демонстрации это 41 таблица
  и около 2 300 строк. Время ответа замеряется в VERIFY Q7 и записано в `docs/runbook/database.md`.
  Когда данных станет на порядки больше, записи переводятся на SQL по одной, под паритетным
  тестом.

## Что не делаем

- **Воркер распознавания документов.** Загрузка в серверном контуре по-прежнему имитирует
  распознавание.
- **Роли базы с ограничением строк (RLS).** Права проверяет обёртка портов ADR-012.
- **Проверку на настоящем Neon.** Драйвер написан по документации, проверен локально только
  драйвер `pg`. Первый запуск на Neon — отдельный шаг из runbook.
