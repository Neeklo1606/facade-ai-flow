# ADR-060. Сервис v1: контракты, база и передача на бэкенд

Дата: 31.10.2026. Статус: принято (S8).
Основание: docs/design/GAIKA_SERVICE_V1_PROMPTS.md, раздел S8; ADR-005 (адаптер базы,
мост снимка), ADR-056, ADR-057, ADR-058.

## Task Brief

Цель: подготовить модули сервиса v1 (S4–S6) к переносу на сервер:

- контракты zod сущностей;
- миграции PostgreSQL и сиды демо;
- вторая реализация хранения;
- проверка на чистой базе;
- документ передачи и отчёт приёмки.

Класс T2:

- рабочая база не трогается, проверка идёт на временной базе локального PostgreSQL 16;
- ключей и живых сервисов нет;
- в `main` не сливается до «ок» владельца.

### Расхождения с постановкой

- **Порты с двумя реализациями.** Сделано для снабжения и документов. Учёт времени
  (`GasOpsPort`) хранится в базе тем же хранилищем, но его 24 метода пока читают вкладку
  напрямую. Перевод механический, по готовому образцу, но затрагивает экраны и тесты S4,
  которые уже работают. Он записан первой задачей бэкенда (docs/BACKEND_HANDOFF.md, 9.5).
- **Серверные функции с проверкой прав** не сделаны. В демо пользователь `/gas` — это
  `actorId` в снимке, а не сессия, поэтому серверу некого проверять. Права проверяет порт
  до любого изменения, одинаково над вкладкой и над базой. Вход ролей `/gas` и функции
  поверх порта — задачи 2 и 3.
- **Пары снимков с референсом.** Скриншотов референсов владельца в репозитории нет
  (`docs/design/service-v1/refs/README.md`). Отчёт приёмки показывает десять пар
  «компьютер 1440 / телефон 390» тех же экранов.

## Решение

**Контракты.** `src/contracts/gas.ts` собран на тех же `table()`/`col`, что основная база.

- 27 таблиц и 13 перечислений.
- Ключи текстовые (`col.key`, `col.keyRef`): их создаёт приложение, демо и база хранят один
  ключ, перевода в uuid нет.
- Имена полей совпадают с domain.
- Реестр `gasTables` свой: модули не участвуют в паритете основного приложения.

**Миграция.** Её генерирует `bun run db:gas-schema` из контрактов. Тест
`tests/db/gas-contracts.test.ts` держит файл равным выводу генератора, а `check:db` сверяет
базу с контрактами колонка в колонку.

- Ключи отправки с телефона уникальны частичными индексами.
- Журналы `gas_reviews` и `gas_audit` — только `insert`.
- Без внешних ключей, где их не допускает домен:
  - `gas_crew_members.employee_id`, `gas_rates.employee_id`: демо-монтажники есть только
    в составе;
  - `gas_supply_requests.chosen_offer_id`: взаимная ссылка.
- Состояние до S4 лежит одной строкой jsonb `gas_state`. Это черновик, нормализация —
  задача бэкенда.

**Хранилище.** `src/adapters/gas-ops/store.ts` задаёт интерфейс `GasStore` с двумя
реализациями:

- `demoStore` — вкладка;
- `createGasDbStore(driver)` — мост снимка, как у адаптера основной базы (ADR-005):
  - согласованное чтение всех таблиц модулей;
  - тот же код порта;
  - разница одним пакетом;
  - время в поясе `APP_TIME_ZONE`.

Кодек снимка и строк — `db-codec.ts`. Адаптеры снабжения и документов получают хранилище
параметром.

**Одновременная запись.** Порт решает по снимку, прочитанному в начале действия (номер
заявки, проверка правил). Поэтому версия сверяется со снимком, по которому принято решение,
а не со снимком, перечитанным перед записью:

- первый оператор пакета увеличивает `gas_versions`, только если версия совпала,
  иначе деление на ноль откатывает пакет;
- конфликт даёт `GasStaleError`;
- `retrying(port)` повторяет действие целиком: заново чтение, правила, номер.

Повтор одной лишь функции изменения оставлял старый номер. Это поймал уникальный индекс
номера заявки в первом прогоне проверки.

**Проверка на чистой базе** — `scripts/check-db-gas.ts` в `check:db`:

- сид записан и прочитан без потерь;
- путь S5 → S6 (18 шагов, три отказа по правилам) даёт одинаковые ответы и итоговый снимок
  во вкладке и в базе;
- две заявки из двух хранилищ одновременно: обе на месте, номера разные.

Откат миграции проверен вручную: `up → rollback → up`, после отката 0 таблиц модулей.

**Сиды демо.** `bun run db:gas-seed` пишет публичный набор «Демо-подрядчик» только в пустую
базу.

### Найдено при аудите прав и исправлено

Правила учёта времени (S4) перечисляли запреты: «кроме бригадира», «кроме руководителя».
Роли S5–S6 (прораб, снабженец, ПТО) появились позже и проходили эти правила через порт:
могли подтвердить запись с суммой, загрузить смету, поменять состав.

Теперь у действий список разрешённых ролей (`TIME_ROLES`, `mustManager`). Поведение прежних
ролей не изменилось. Тест `tests/negative/gas-module-roles.test.ts` на старом коде падает
(3 из 4), на новом проходит.

### Найдено на снимках приёмки и исправлено

В поиске совпадение на выбранной (чёрной) строке было невидимо: подсветка задавала цвет
текста `ink`. Теперь она берёт цвет текста строки (`SearchPalette.tsx`).

### Мусор в истории

В коммит S7 попали две копии временного скрипта снимков (`lp 2.ts`, `lp 3.ts`), которые
создала синхронизация папки `~/Documents`. Они удалены коммитом S8, историю не переписывали.
