# ADR-001. Единая модель данных и слой доступа к ней

- **Статус:** принято
- **Дата:** 2026-09-16
- **Контекст коммита:** `ef7a93f`
- **Решает дефекты:** D1 (две модели данных), D2 (нет слоя доступа), частично D4 (генерация данных в клиенте)
- **Связано:** [ADR-002](ADR-002-state-and-persistence.md), [ARCHITECTURE.md](../../ARCHITECTURE.md)

## Контекст

В проекте живут две независимые модели предметной области:

- старая: `src/mock/sites|tasks|supply|events|agents|users` + типы в `src/types/index.ts` (320 строк);
- новая: `src/mock/repository/*` + типы в `src/mock/repository/types.ts` (707 строк).

На старой модели держатся 9 файлов, в том числе дашборд `/`, `/inbox`, `/verification`, агент
(`lib/agent-engine.ts`, `AgentDock`), а также `app-context` и `Topbar`. Остальные экраны читают новую модель.

Следствия, зафиксированные аудитом:

1. Одна и та же величина имеет два значения. «ЖК Северная Корона»: старая модель — договор СИ-2026/041,
   47,2 млн, 62 %, срок 30.11.2026; новая — ДСК-2026/008, 95,4 млн, 43,4 %, срок 31.03.2027. Номера
   договоров у «Короны» и «Приморского квартала» поменяны местами между моделями.
2. Дашборд смешивает источники: незакрытый объём берёт из `repository`, объекты и риски — из старых моков.
3. Число позиций спецификации существует в двух наборах: `specItems` (9 строк, показывает глобальная
   `/documents`) и `extractedPositions` (847 строк, показывает экран объекта).
4. Потребность в материалах расходится: `materials.mt-bracket.need` = 12 400 шт против 13 930 шт
   суммой по позициям спецификации.
5. Новые экраны не видят данные друг друга через общий контракт: созданный в демо запрос
   З-2026/326 виден в закупке объекта и отсутствует в глобальном `/requests`, потому что тот читает моки напрямую.
6. Моки импортируются в 39 файлах `components/` и `routes/`. Слоя доступа нет.
7. `checkConsistency()` существует, проверяет только деньги и объёмы и нигде не вызывается.

## Рассматриваемые варианты

### A. Оставить как есть, чинить расхождения вручную
Дешёво сейчас, но каждая новая величина снова разъезжается. Подключение API — правка 39 файлов.
Отклонено.

### B. Смэпить старую модель на новую адаптером, старые экраны не трогать
Дешевле переезда, но фиксирует два словаря навсегда и оставляет 39 прямых импортов.
Отклонено: не снимает ни D1, ни D2.

### C. Сразу подключить внешнее хранилище и писать экраны против него
Снимает дефекты, но требует готовой схемы БД и контрактов, которых нет; блокирует демонстрации
на время миграции. Отклонено как первый шаг. Хранилище выбрано — PostgreSQL в горизонте фазы 3,
поэтому контракты сразу проектируются как задание на его схему (см. п. 8 решения).

### D. Контракты на zod + порты репозиториев + серверные функции, демо-данные как один из адаптеров
Принято.

## Решение

1. **Источник истины — `src/contracts/*.ts`:** схемы zod на каждую сущность, типы выводятся
   через `z.infer`. Руками типы не пишем. `src/types/index.ts` и старые моки удаляются.
2. **Доступ к данным — только через порты.** Для каждой области (`projects`, `documents`,
   `positions`, `procurement`, `reports`, `timeline`) объявляется интерфейс репозитория:
   методы чтения и мутаций, аргументы и результаты описаны схемами из `contracts`.
3. **Реализации портов — адаптеры.** `adapters/fixtures` — демо-данные (текущие моки, приведённые
   к схемам, плюс симулятор событий из ADR-002). `adapters/db` — реальное хранилище, появляется в фазе 3.
   Выбор адаптера — переменная окружения, экраны об этом не знают.
4. **Транспорт — серверные функции TanStack Start** (`createServerFn`). Инфраструктура уже есть:
   `src/start.ts` подключает CSRF-мидлвар для `serverFn`. Валидация входа — схемой contracts,
   на выходе — тоже схема. Это же место для авторизации и записи в аудит.
5. **Запрет прямых импортов данных в отображении.** ESLint `no-restricted-imports`:
   `@/mock/*` и `@/adapters/*` запрещены в `src/components/**` и `src/routes/**`.
6. **Один словарь статусов и подписей на сущность** — в `contracts` рядом со схемой. Сейчас
   словарь статусов запроса продублирован в четырёх файлах.
7. **Удалённые экраны не переносятся** (ADR-003): старый дашборд, агент и глобальные экраны
   убраны из продукта, их функциональность возвращается позже на единой модели.
8. **Контракты — сразу задание на схему PostgreSQL.** Хранилище выбрано: PostgreSQL в горизонте
   фазы 3. Поэтому каждая схема в `contracts` проектируется не как форма ответа экрана, а как таблица:
   - первичный ключ `uuid`, внешние ключи с явным поведением при удалении (`restrict` для документов
     и решений, `cascade` только для строк, которые не живут без родителя — строки предложения, листы документа);
   - деньги — целые копейки (`bigint`), количества — `numeric(14,3)`, единицы измерения — справочник;
   - статусы — перечисления (`enum`) с явным списком переходов, а не свободные строки;
   - `created_at`, `updated_at`, `created_by` на каждой изменяемой сущности; решения и изменения
     позиций — только добавлением, без обновления (журнал);
   - для каждого списка на экране — индекс под его фильтр и сортировку: позиции по
     `(document_id, sheet_number, position)` и `(project_id, review_status)`, запросы по `(project_id, status, reply_due_at)`,
     события истории по `(project_id, occurred_at desc)`, отчёты по `(project_id, report_date desc)`;
   - уникальность, которую сейчас держит только соглашение: номер запроса в пределах года,
     номер позиции в пределах листа документа, ревизия в пределах документа.
   Результат задачи P1-2 — схемы zod и документ `docs/db/schema.md` с ER-диаграммой, таблицами, связями и индексами.
9. **Согласованность проверяется машиной.** Вместо неиспользуемой `checkConsistency()` —
   тесты на инварианты: «сумма позиций по семейству = потребность материала», «проверено + непроверено = всего»,
   «закрытое + незакрытое = выполненное». Запускаются в CI на фикстурах.

## Последствия

**Плюсы**
- Одна величина считается в одном месте; расхождения между экранами становятся невозможны без падения теста.
- Подключение реального хранилища — замена адаптера, а не правка 39 файлов.
- Демо-данные остаются рабочими на всех фазах: они просто другой адаптер.
- Серверные функции дают точку для прав доступа и аудита, которых сейчас нет вообще.

**Минусы и цена**
- 11,5 человеко-дня на фазу 1 (см. TASKS.md P1-1…P1-8). Проектирование схемы под PostgreSQL
  дороже формы ответа: P1-2 оценена в 4 дня вместо 3.
- Решение по дашборду, агенту и глобальным экранам вынесено в ADR-003: удаляются в фазе 0.
- Схемы zod дают рантайм-проверку, это небольшой оверхед на больших списках; для списка позиций
  валидируем ответ целиком один раз на сервере, а не на каждый элемент в клиенте.

## Условия приёмки

- `grep -r "@/mock" src/components src/routes` не находит совпадений.
- Одна предметная область — один набор типов; `src/types/index.ts` удалён.
- `docs/db/schema.md` описывает таблицы, связи, перечисления и индексы для каждого списка на экранах.
- Все экраны, оставшиеся в продукте, читают данные через хуки поверх портов.
- Тесты инвариантов согласованности проходят на фикстурах в CI.
