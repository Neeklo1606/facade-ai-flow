# ADR-035. Шлюз моделей: адаптеры и границы данных

Дата: 18.10.2026. Статус: принято. Шаг G3 очереди сборки.

## Контекст

`GAIKA_AI_GATEWAY.md` требует собственный шлюз: модели подключаются через порт, меняются
переменной окружения, каждый вызов записывается, ответ проходит схему. В коде на 18.10.2026
нет ни одного обращения к языковой модели и к распознаванию речи: в G0 весь документ был
помечен `planned`.

Решения ниже приняты до кода, как требует очередь.

## 1. Какие адаптеры делаем сейчас

| Адаптер                               | Что закрывает                                                     | Делаем в G3             |
| ------------------------------------- | ----------------------------------------------------------------- | ----------------------- |
| `OpenAiCompatibleLlm`                 | DeepSeek, OpenAI, OpenRouter — один chat API с JSON-режимом       | да                      |
| `DemoLlm`                             | `AI_MODE=demo`: подготовленные разборы трёх сценариев, без ключей | да                      |
| `OpenAiSpeech`                        | распознавание речи OpenAI, отдельный порт                         | да                      |
| `DemoSpeech`                          | расшифровка подготовленных голосовых демо                         | да                      |
| YandexGPT, GigaChat, Yandex SpeechKit | российский контур                                                 | нет, отдельным решением |

Один адаптер на трёх провайдеров, потому что различие между ними — адрес, ключ и имя модели,
а не протокол. Как только провайдер потребует другого формата авторизации или другого тела
запроса, у него появится свой адаптер: признак — не бренд, а протокол.

Речь отделена от текста намеренно: DeepSeek речь не распознаёт, и провайдеры выбираются
независимо (`LLM_PROVIDER` и `STT_PROVIDER`).

## 2. Границы данных

1. **Вызов только с сервера.** Ключи читаются через `serverEnv` и на клиент не попадают.
   В демонстрации данные живут во вкладке, поэтому там работает только заглушка: ключа в браузере
   нет и быть не может.
2. **В модель уходит только то, что нужно для разбора:** текст сообщения и контекст объекта
   (участки, виды работ с единицами, бригады, люди, ожидаемые материалы, рабочая дата).
   Ни цен, ни договоров, ни контактов, ни персональных данных сверх имён сотрудников объекта.
3. **Текст сообщения — данные, а не инструкции.** Это сказано в системном промпте и проверено
   тестом: сообщение с «игнорируй инструкции» не меняет поведение, его разбор остаётся разбором.
4. **Внешние модели вне российского контура.** Демо и лендинг работают только на синтетических
   данных. Реальные данные уходят во внешнюю модель только после согласования: получатель,
   состав данных, хранение. Иначе российский провайдер или модель в контуре клиента.
5. **Ни аудио, ни токены, ни ключи в обычные логи.** В `ProcessingJob` пишутся провайдер, модель,
   версия промпта, длительность, число токенов и оценка стоимости — не содержимое запроса.
6. **Ответ модели не попадает в учётные поля.** Схема zod отбраковывает невалидный ответ целиком,
   а валидный становится черновиком, который подтверждает человек (правило 1). Применение
   черновиков к записям — шаг G5, здесь их только получают и записывают работу.

## 3. Что именно записывается

Таблица `processing_jobs`: объект, источник, вид работы (`transcribe`, `extract`, `draft`,
`answer`), провайдер, модель, версия промпта, статус (`ok`, `invalid`, `failed`), длительность,
токены запроса и ответа, оценка стоимости в копейках, причина отказа и сам результат разбора
в `jsonb`. Таблица только добавляется (`appendOnly`): это журнал, а не состояние.

Оценка стоимости считается по прайсу провайдера из конфигурации, а не выдумывается: модели,
цены которой нет, записывается `null` — «неизвестно остаётся неизвестным» (правило 3).

## 4. Версия промпта

Промпт извлечения лежит в `src/ai/prompts/extract.ts` с константой версии. Документ просит
`packages/ai/prompts`; репозиторий — модульный монолит, и документ разрешает ближайший аналог.
Версия пишется в каждую обработку: без неё нельзя сравнить два прогона оценки.

## 5. Оценка качества

Набор `evals/messages.ts`: 30 синтетических сообщений с эталонным разбором — чистый текст,
шумная речь, несколько работ в одном сообщении, отрицания и исправления, неоднозначные единицы,
два объекта с похожими названиями, попытка подменить инструкции.

`bun run eval:extract` прогоняет набор через выбранный шлюз и печатает точность по полям,
полноту обязательных полей, критические ошибки (объект, дата, количество, единица, двойной учёт),
время и стоимость. Отчёт с версией модели и промпта сохраняется в `evals/reports`.

В демо-режиме набор проходит по подготовленным разборам: это проверка самой оценки, а не модели.
Живой прогон требует ключа. **Ключа у агента нет**, поэтому живые цифры в отчёте о шаге
не приводятся: без ключа это было бы выдумкой.

## 6. Что отвергнуто

Писать в модель весь контекст объекта целиком, включая цены и договоры: модель не выбирает
поставщика и не считает деньги, а каждое лишнее поле — это данные, которые ушли наружу.

Хранить разбор только в памяти процесса до G5: тогда нельзя сравнить два прогона оценки
и нельзя показать человеку, откуда взялось значение. Журнал обработок — часть правила
«у каждого значения есть источник».

Единый порт на речь и текст: у них разные провайдеры, разные лимиты и разные единицы
стоимости (секунды против токенов).
