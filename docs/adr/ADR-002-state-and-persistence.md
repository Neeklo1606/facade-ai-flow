# ADR-002. Состояние приложения, персистентность и демо-режим

- **Статус:** принято
- **Дата:** 2026-09-16
- **Контекст коммита:** `ef7a93f`
- **Решает дефекты:** D3 (синглтон в памяти), D5 (демо-механика в продукте), частично D4 (расчёты в клиенте)
- **Связано:** [ADR-001](ADR-001-data-layer.md), [ARCHITECTURE.md](../../ARCHITECTURE.md)

## Контекст

Все действия пользователя (подтверждение позиций, загрузка документов, создание запросов, решения,
приёмка отчётов) складываются в `src/lib/spec-store.ts` — модульную переменную с ручным
`set`/`subscribe` и `useSyncExternalStore`.

Зафиксировано аудитом:

1. **Перезагрузка страницы стирает всё.** Хранилище живёт в памяти модуля, персистентности нет.
   На демонстрации любое обновление страницы обнуляет показанный путь.
2. **Подписка на весь стор** в трёх местах (`useSpecStore((s) => s)`), включая экраны со списками
   на 847 строк — лишние перерисовки.
3. **Загрузка имитируется:** `useSimulatedLoading(350)` показывает скелетон на каждом экране,
   за ним нет запроса. Стадии обработки документа — цепочка `setTimeout` в хранилище.
4. **Состояние экрана задаётся адресом:** `?state=empty|error|forbidden|…` и переключатель
   `StatePicker` в шапке рабочего интерфейса. Посторонний может выключить экран в «Нет доступа».
5. **Время двойное:** просрочки считаются от зашитого `MOCK_NOW = 2026-09-05`, а действия пользователя
   получают реальную дату. В истории сегодняшние события уезжают выше блока «Сегодня, 5 сентября».
6. **Часть сценария физически не может продолжиться:** для созданного запроса предложения
   не приходят никогда, «Зафиксировать решение» заблокировано. Цепочка рвётся между шагами 5 и 6.
7. `QueryClient` уже создан (`src/router.tsx`) и роздан провайдером, но ни одного `useQuery`
   в коде нет: восемь маршрутов используют `loader` только для проверки существования объекта.

## Рассматриваемые варианты

### A. Оставить синглтон, добавить сохранение в `localStorage`
Снимает только пункт 1. Кеш, инвалидация, состояния загрузки и ошибок остаются ручными,
а при подключении API логика перепишется целиком. Отклонено.

### B. Zustand или Redux Toolkit
Аккуратнее текущего синглтона, но клиентский стор всё равно начнёт дублировать серверные данные;
понадобится ручная синхронизация после мутаций. Отклонено: серверные данные — не место для стора состояния.

### C. TanStack Query как единственное место серверных данных + router loaders, локальный UI-стейт в React и адресе
Принято.

## Решение

1. **Серверное состояние — TanStack Query.** Ключи запросов описываются в `src/api/keys.ts`,
   чтение — хуками `useProject`, `usePositions`, `useRfq` и так далее поверх серверных функций (ADR-001).
   Предзагрузка для критичных экранов — через `loader` маршрута (`queryClient.ensureQueryData`),
   чтобы SSR отдавал готовые данные.
2. **Мутации — `useMutation` с точечной инвалидацией.** Подтверждение позиции, создание запроса,
   фиксация решения, приёмка отчёта оптимистично обновляют список и инвалидируют затронутые ключи.
   «Отменить» в уведомлении реализуется как обратная мутация, а не как правка объекта в памяти.
3. **`lib/spec-store.ts` удаляется.** Клиентское состояние остаётся только там, где оно действительно
   клиентское: выбранная позиция, открытая вкладка, фильтры (в адресе), свёрнутые группы, тема, боковая панель.
4. **Состояния экрана выводятся из данных, а не задаются адресом.** `ScreenGate` остаётся, но получает
   `isPending`, `isError`, `isForbidden` (из ответа сервера), пустой и отфильтрованный результат.
   `useSimulatedLoading` удаляется. Параметр `?state=` и `StatePicker` уходят за флаг `VITE_DEMO`
   и не собираются в рабочую сборку.
5. **Демо-режим — отдельный адаптер, а не поведение интерфейса.** В `adapters/fixtures` живут:
   seed-данные, «часы демо» (одно время для всех, вместо `MOCK_NOW` и реальной даты одновременно),
   симулятор событий — ответ поставщика через несколько секунд после отправки запроса, прохождение
   стадий распознавания, доставка. Именно он закрывает обрыв сценария на шаге 6.
6. **Персистентность демо.** Состояние адаптера сохраняется в `sessionStorage` и восстанавливается
   при перезагрузке; сброс — отдельная кнопка «Начать демо заново» в демо-режиме.
   В рабочем режиме персистентность не нужна: источник истины — сервер.
7. **Длительные операции — задачи со статусом.** Распознавание документа становится задачей
   (`queued → recognizing → extracted → review`), интерфейс опрашивает её статус. Никаких `setTimeout`
   в рабочем коде: таймеры допустимы только внутри демо-адаптера.

## Последствия

**Плюсы**
- Перезагрузка перестаёт обнулять сценарий; демонстрацию можно вести без страха обновить страницу.
- Скелетон показывается, когда данные действительно грузятся, а не 350 мс всегда.
- Экран «нет доступа» перестаёт быть фокусом и становится следствием прав.
- Сквозной путь замыкается: предложения приходят, решение фиксируется, история пополняется.
- Убирается двойное время: одно «сейчас» на весь режим.

**Минусы и цена**
- 15 человеко-дней на фазу 2 (TASKS.md P2-1…P2-6), включая перевод девяти экранов на хуки данных.
- Оптимистичные обновления требуют аккуратных ключей: ошибка в ключе даёт «мигающие» списки.
  Снимается тестами на мутации (P5-1) и явной таблицей ключей в `api/keys.ts`.
- Демо-режим становится кодом, который надо поддерживать. Это осознанная плата: он же служит
  тестовым стендом для сквозных тестов (P5-3).

## Ход реализации

- Фаза 2 — TASKS.md «Итоги фазы 2», уточнения — ADR-004.
- П. 7, фаза 3: распознавание — задача `extraction_jobs` со статусом, интерфейс опрашивает её, пока она
  не завершена (`src/api/queries.ts`, `src/api/extraction.ts`). Таймеры — только в демо-адаптере.

## Условия приёмки

- `src/lib/spec-store.ts` удалён, `useSimulatedLoading` удалён, `MOCK_NOW` не встречается за пределами `adapters/fixtures`.
- Ни один компонент не подписывается на состояние целиком.
- Сквозной сценарий проходится до конца и выживает перезагрузку страницы.
- В рабочей сборке нет `StatePicker` и обработки `?state=`.
