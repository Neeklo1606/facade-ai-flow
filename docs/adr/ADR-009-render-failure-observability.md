# ADR-009. Видимость отказов отрисовки: сквозной номер запроса, структурированная запись, порог уведомлений

- **Статус:** принято
- **Дата:** 2026-09-19
- **Задача:** диагностика отказов серверной отрисовки, этап 1 «Видимость»
- **Связано:** [ADR-004](ADR-004-demo-adapter-in-browser.md) (демо-адаптер в браузере),
  [RUNBOOK §7](../RUNBOOK.md#7-наблюдаемость)

> **Состояние на 25.09.2026.** Решение принято и записано, реализация живёт в невлитой ветке
> `ssr-observability`. В `main` этот файл лежит как запись решения: без него в нумерации ADR была дыра,
> а ссылки из README и соседних решений вели в никуда. Что из решения уже действует в `main`,
> сказано в [STATE.md](../STATE.md).

## Контекст

Отчёт приёмки: «пустая /admin через раз, за сутки 7 ответов 500 на /, в журналах ничего».
Прежде чем искать причину, нужно было выяснить, почему отказы не видны вовсе.

Четыре управляемых сбоя на локальной боевой сборке (рабочий контур, полный SSR) показали, где
обрывается цепочка:

| Сбой                                      | Ответ   | Что было в журнале                                                                                                                                                                 |
| ----------------------------------------- | ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| исключение до отрисовки (`src/server.ts`) | 500     | стек свободным текстом: ни маршрута, ни метода, ни номера запроса                                                                                                                  |
| исключение загрузчика маршрута            | **500** | **ничего.** Роутер ловит исключение сам и превращает его в состояние маршрута; `console.error` на сервере не вызывает никто. Экран — встроенный английский «Something went wrong!» |
| исключение при отрисовке компонента       | **200** | «Error in renderToReadableStream» свободным текстом. По коду ответа отказ не виден                                                                                                 |
| сбой загрузки данных экрана (`prefetch`)  | **200** | **ничего.** Ошибка глушится намеренно, чтобы экран показал «Ошибка» с повтором                                                                                                     |

В публикуемом **демо-контуре** серверная отрисовка маршрутов выключена (`src/start.ts`,
`defaultSsr: dataSource === "server"`): сервер отдаёт пустую оболочку, экран рисует браузер.
Там сбой отрисовки — это сбой в браузере при ответе 200, и увидеть его может только сама страница.

Нет ни php-fpm, ни nginx: стек — TanStack Start на nitro, хостинг — Lovable поверх Cloudflare
Workers. Журнал — вывод `console` воркера.

## Решение

1. **Сквозной номер запроса.** Генерируется на входе в `src/server.ts`. За Cloudflare это `cf-ray`
   (по нему же запрос находится в панели Cloudflare), без Cloudflare — UUID. Значение от клиента
   не принимается. Номер уходит:
   - в запрос — заголовком `x-request-id`, серверный код читает его оттуда;
   - в ответ — заголовками `x-request-id` и `Server-Timing: rid;desc="…"`. `Server-Timing` скрипт
     страницы читает без переписывания HTML, поэтому экран ошибки и отчёт браузера знают номер загрузки;
   - на экран 500 сервера и на экран ошибки маршрута — чтобы пользователь мог его назвать.

2. **Структурированная запись, отдельный канал.** Каждый отказ — одна строка JSON с
   `"channel":"ssr-error"` через `console.error`. На node-сервере строка дублируется в файл
   `SSR_ERROR_LOG`. Поля: `at`, `kind`, `status`, `method`, `route`, `requestId`, `session`,
   `persona`, `build`, `durationMs`, `errorName`, `message`, `stack`, `extra`.

   `session` — анонимная cookie `fo_sid`: случайная строка до закрытия браузера, не ключ доступа
   и не личные данные. `build` — коммит и время сборки, время есть всегда, даже без `.git`.

3. **Классы отказа** (`kind`), по одной записи на запрос:

   | kind                                        | Где ловится                                                                                                                          |
   | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
   | `entry`                                     | исключение на входе или в промежуточном слое                                                                                         |
   | `loader`                                    | `onError` каждого маршрута. Общего обработчика у роутера нет, поэтому `onError` оборачивается один раз на маршрут в `src/router.tsx` |
   | `render`                                    | маркер React `<!--$!-->` в потоке HTML: граница не отрисовалась на сервере                                                           |
   | `stream`                                    | обрыв потока после отправки заголовков                                                                                               |
   | `data`                                      | неудачная предзагрузка данных экрана на сервере                                                                                      |
   | `status_5xx`                                | нижний этаж: любой 5xx получает запись, даже если исключение до сервера не дошло                                                     |
   | `client`, `empty_screen`, `app_not_mounted` | отчёты браузера                                                                                                                      |

4. **Сторож пустого экрана** — строка скрипта в `<head>`, не зависит от бандла. Через 15 секунд
   после загрузки он проверяет, запустилось ли приложение и есть ли текст в основной области.
   Если нет — маяк на `/api/client-error` с номером запроса страницы. Это единственный способ
   увидеть класс «200, а на экране пусто» в демо-контуре. Проверено: на 15 рабочих экранах,
   на `/admin` и заглушках, на десктопе и телефоне ложных срабатываний нет.

5. **Счётчики и уведомление.** Скользящее окно в час, два счётчика: ответы 5xx и отказы при 200
   (`render`, `stream`, `data`, `empty_screen`, `app_not_mounted`). Больше трёх за час —
   одно уведомление на класс в час, POST JSON на `ALERT_WEBHOOK_URL`. Поля `text` и `content`
   подходят для Telegram, Slack и Discord. Само уведомление пишется в журнал всегда (`ssr-alert`),
   неудачная доставка — тоже (`ssr-alert-failed`).

## Ограничения, известные при принятии

- **Счётчик живёт в экземпляре воркера.** Общей памяти между экземплярами у Cloudflare нет.
  При нескольких экземплярах каждый считает свои отказы, и порог может не сработать, хотя в сумме
  он превышен. Для демонстрации с малым трафиком экземпляр обычно один, но это не гарантия.
  Точный счёт по сайту требует хранилища — Durable Object или KV. Это решение владельца:
  привязки хранилища настраиваются на хостинге.
- **Сохранность журнала зависит от хостинга.** Если в Cloudflare выключены Workers Logs, вывод
  воркера никуда не сохраняется, и записи видны только в живом просмотре (`wrangler tail`).
  Тогда единственный надёжный канал — вебхук. Проверить это можно только в кабинете Lovable
  или Cloudflare.
- **Отчёты браузера можно подделать** тому, у кого есть ключ доступа: приём открыт. Для
  демонстрации это приемлемо. Если по ложным отчётам начнут приходить уведомления, нужен
  лимит на сессию.
- **Сторож срабатывает, только если страница открыта дольше 15 секунд.** Ушедший раньше
  пользователь отчёта не оставит.

## Что не делаем

- Не угадываем причину 500 на `/` и пустой `/admin`: это этап 2, по данным минимум за сутки.
- Не подключаем внешние сервисы сбора ошибок (Sentry и подобные). Решение TASK-A5 — свой
  эндпоинт, без внешних аккаунтов — остаётся в силе.

## Расширение от 2026-09-19: захват контекста, пустая `/admin`, сканеры

### Пустая `/admin` — следствие локальных условий, не дефект продукта

Проверено сериями по 20 загрузок `/admin` в свежем браузере; «пусто» — экран «Раздел не найден»
не появился к отсечке. Фон машины во всех сериях — синхронизация iCloud (`fileproviderd` ~1 ядро),
свободной памяти 50–220 МБ из 8 ГБ, подкачка 3–5 ГБ.

| Сервер                  | Условия                                  | Загрузка  | Экран, медиана / макс | Пусто на 2 с / 5 с / 10 с |
| ----------------------- | ---------------------------------------- | --------- | --------------------- | ------------------------- |
| боевая сборка           | фон iCloud                               | 7,0–7,8   | 0,8 / 1,1 с           | 0 / 0 / 0 из 20           |
| боевая сборка           | фон + 8 процессов нагрузки               | 20,5–23,8 | 0,8 / 1,1 с           | 0 / 0 / 0 из 20           |
| dev, прогретый          | фон iCloud                               | 8,6–9,2   | 1,0 / 1,9 с           | 0 / 0 / 0 из 20           |
| dev, прогретый          | фон + 8 процессов                        | 33,4–37,5 | 1,1 / 1,7 с           | 0 / 0 / 0 из 20           |
| dev, прогретый          | перегрузка (незапланированная, см. ниже) | 46–53     | 1,6–2,1 / 16,4 с      | 4–11 / 1–2 / 0–1 из 20    |
| dev, **холодный старт** | фон iCloud                               | 14,6–24,3 | 11,5 / 15,9 с         | 5 / 5 / 3 из 5            |
| dev, **холодный старт** | фон + 8 процессов                        | 31,6–48,0 | 18,2 / 28,4 с         | 5 / 5 / 5 из 5            |

Перегрузка 46–53 случилась из-за ошибки при остановке процессов нагрузки: они дожили до
самозавершения. Серия не планировалась, но показывает границу, поэтому оставлена.

Вывод: **боевая сборка пустую `/admin` не даёт ни при какой проверенной загрузке**, включая
втрое выше приёмочной. Пустую страницу даёт только сервер разработки (`vite dev`): на первом
заходе после старта его оптимизатор зависимостей пересобирает их и перезагружает страницу
(`optimized dependencies changed. reloading` в журнале), и 8–28 секунд экран пуст; под нагрузкой
дольше. «Через раз» объясняется этим: первые заходы после запуска или смены зависимостей
пустые, прогретые — нет. Приёмка шла на локальной машине, значит, почти наверняка на dev-сервере.
Статус: ложный дефект, закрыт.

Оговорка: серии на тихой машине нет — остановить синхронизацию iCloud можно только в системных
настройках. Вывод от неё не зависит: сравнение боевой сборки и dev-сервера шло в одинаковых условиях.

### Захват контекста отказа

- **Длина тела каждого ответа 200** — строка в канале `ssr-access`: маршрут, код, байты, тип,
  номер запроса, время ответа. Отдельно от `ssr-error`, чтобы отказы не тонули.
- **Класс `short_200`** — ответ 200 с аномальным телом: пустое тело; HTML короче 1 КБ, притом
  что самая короткая настоящая страница — объяснение для краулеров, ~3 КБ; HTML без `</html>`.
  На полном прогоне сценариев в обоих контурах — 0 ложных срабатываний на 4810 ответах.
- **Снимок состояния** в записи каждого 5xx и аномального 200, снятого на сервере: запросы в
  обработке, открытые сокеты, память процесса, средняя загрузка, свободная память ОС, открытые
  дескрипторы. **Пула соединений в проекте нет** — рабочий контур читает данные из памяти
  процесса, поле `pool` всегда `null`. На Cloudflare Workers процесса и ОС нет: снимок
  помечается `source: "worker"` с нулями, вместо заглушек `node:os`, выданных за измерение.
- **Кольцевой буфер** последних 20 записей журнала приложения — все уровни `console` —
  выгружается в поле `preceding` записи отказа.
- **Порог уведомления** — один отказ за час. Уведомление уходит на каждый отказ, но не больше
  пяти на класс в час: каскад не превращается в шторм сообщений, остальное — только журнал.

### Ограничение частоты для сканеров

Десять подряд ответов «нет такого адреса» с одного адреса клиента за минуту — 429 на 10 минут
с `Retry-After`. Сигнал — 404, а при включённом шлюзе ещё и 401: без ключа сканер 404 не видит.
Не считаются 404 по `/assets/`: это открытые вкладки после публикации, их чанки исчезли.
Любой успешный ответ сбрасывает счёт. Запросы с правильным ключом или действующей cookie
доступа не ограничиваются никогда. Адрес клиента — `cf-connecting-ip`; без адреса ограничение
не применяется. Состояние живёт в экземпляре воркера; полноценная замена — правила частоты
Cloudflare WAF, это настройка владельца.

Проверено:

- сканер ограничен на 11-м запросе и со шлюзом, и без;
- посетитель рядом, человек с опечатками, старые чанки, краулер превью и вошедший пользователь
  за адресом сканера не задеты;
- полный прогон сценариев через прокси с адресом клиента — 4810 ответов, ни одного 429.
