# ADR-069. Рабочий контур учёта времени для сопровождаемого пилота

Дата: 12.11.2026. Статус: принято. Основание: указание владельца от 12.11.2026 («подготовь
к деплою на реальных задачах клиента»). Связанные: ADR-061 (решение 14, серверные функции),
ADR-021 (вход), ADR-068 (образ для сервера), BACKEND_HANDOFF 9.5, задача 2.

## Что было

Сборка `server` с PostgreSQL проходила правила тем же кодом, что демо, но настоящий человек
до них не доходил:

1. Сессия даёт идентификатор сотрудника (`employees`), а учёт времени ищет пользователя
   `gas_users` с тем же идентификатором. Ни одна команда и ни один экран такого пользователя
   не заводили: каждое действие на `/gas` отвечало 403.
2. Пустая база после `db:migrate` не имела строки состояния; единственный путь заполнения,
   `db:gas-seed`, пишет демо-набор «Демо-подрядчик».
3. «Сегодня» и неделя лежали в строке состояния и не сдвигались: неделя закрывалась один раз.
4. При отказе сервера экраны молча показывали исходный демо-набор.
5. Выгрузка с экрана присылала неделю телом, и сервер собирал файл с суммами из этих данных
   без проверки входа и роли.
6. Ввод за бригаду у менеджера был привязан к демо-идентификатору `brg-1`.

## Решения

1. **Пустая компания** (`src/domain/gas-ops/pilot.ts`, `emptyCompany`): одно подразделение,
   правило стоимости по умолчанию, первый администратор, пустые справочники, снабжение
   и документы. Команда `bun run db:gas-init` пишет её в пустую базу и заводит
   администратора входом: строка `employees` и `gas_users` с одним идентификатором и ссылка
   первого входа на 72 часа, сразу на `/gas`.
2. **Люди пилота**: `bun run db:gas-user --role manager|director|foreman|admin`, бригадиру
   `--brigade` из справочника. Проверка бригады и повтора идёт до записи сотрудника входа.
   Экран приглашения внутри `/gas` и канал кода (SMS или Telegram) остаются решением владельца;
   до него вход по ссылке и `AUTH_CHANNEL=log` для сопровождаемого запуска.
3. **Календарь по часам сервера** (`withRealCalendar`, `advanceCalendar`): каждое чтение
   сверяет день в `APP_TIME_ZONE`, новый день записывается; неделя отчёта понедельник–суббота,
   воскресенье относится к прошедшей. Назад календарь не идёт. Записи прошлых недель остаются.
4. **Связь с сервером на экране** (`GasServerGate`): до снимка пользователя загрузка, при отказе
   причина, «Войти» и «Повторить». Исходный демо-набор на рабочем контуре не показывается.
   В демо-сборке состояние сразу «готово», поведение показа не меняется.
5. **Выгрузка только из хранилища** при подключённой базе: тело экрана сводится к неделе,
   виду и версии, файл собирается из базы с проверкой роли и контрольной суммой. Без базы
   демо по-прежнему присылает данные телом.
6. **Бригада просмотра** — демо-бригада, если она есть, иначе первая из справочника.

## Проверка

- `tests/domain/gas-ops-pilot.test.ts`: неделя, часовой пояс, сдвиг календаря, пустая компания,
  пользователи и бригада просмотра.
- `tests/negative/gas-pilot-flow.test.ts`: от пустой компании через `callGasMethod` под ролями:
  справочники, объект, график, смета, формула, бригадир, проверка, новая неделя; 105 000 ₽.
- `tests/negative/gas-export-store.test.ts`: подставленная сумма из тела не попадает в файл.
- Живой прогон на PostgreSQL: `docs/runbook/pilot.md`.

## Что не входит

Канал кода SMS или Telegram, экран приглашений в `/gas`, хранилище исходных файлов,
изоляция нескольких компаний в одной базе, вебхук MAX (501 до токена), живой ответ агента
без ключа, роль заказчика для личной ссылки без входа.
