# ADR-013. Тесты, автоматические проверки и конвейер

- **Статус:** принято
- **Дата:** 2026-09-20
- **Задача:** Q6 очереди «Тесты и автоматические проверки»
- **Связано:** [ADR-001](ADR-001-data-layer.md) (слои), [ADR-004](ADR-004-demo-adapter-in-browser.md)
  (демо-адаптер), [ADR-011](ADR-011-deliveries-and-acceptance.md), [ADR-012](ADR-012-roles-and-access.md),
  план фазы 5 в `TASKS.md` (P5-1…P5-5)

## Контекст

Автотестов нет. Проверки жили скриптами в `.verify` вне репозитория, с путями к кэшу
конкретной машины, и запускались руками. Правила домена, границы слоёв, EMBER и доступность
держались на внимательности, а не на сборке. В фикстурах уже нашлось расхождение: у запроса
З-2026/324 сумма строк не равна сумме позиций, из которых он собран. Проверка, которая
сравнивала бы экраны между собой, его бы поймала.

## Решения

1. **Модульные тесты и тесты согласованности — `bun test`.** Бегун встроен в среду проекта,
   новых зависимостей нет. План фазы 5 называл Vitest. Выбран `bun test`: алиасы `@/` и строгий
   TypeScript работают без отдельной настройки. Тесты лежат в `tests/`. Для типов нужен
   `@types/bun`.

2. **Согласованность проверяется так, как данные видят экраны.** Тест берёт данные через порты
   демо-адаптера — те же, что у экранов. Сравниваются:
   - строка реестра и карточка объекта;
   - счётчики сводки и фасеты материалов;
   - число запросов и поставок в списках;
   - сумма метрик дашборда и сумма по объектам;
   - хранимые счётчики ревизий и посчитанные по позициям;
   - сумма строк запроса и сумма позиций, из которых он собран.

   Проверка идёт два раза: на стартовых фикстурах и после цепочки действий через порты
   (проверка позиций → передача → запрос → решение → приёмка). Отдельный тест вносит расхождение
   в копию данных и требует, чтобы проверка его нашла: иначе зелёный результат ничего
   не доказывает. Фикстура З-2026/324 исправляется в этой же задаче.

3. **Сквозные тесты — `@playwright/test` на демо-сборке.** Сервер — node-сборка с данными
   в браузере. Каждая роль проходит свой сценарий через экран выбора роли. Общая фикстура роняет
   тест при любой ошибке в консоли. На ключевых экранах каждой роли проверяются:
   - одно оранжевое пятно;
   - отсутствие капса;
   - axe-core (`@axe-core/playwright`) без нарушений уровня serious и critical.

   Локально бегун берёт уже установленный браузер через `PW_CHROMIUM`, в конвейере ставит свой.

4. **Негативные сценарии — на двух уровнях.**
   - **Правило в адаптере.** Тест вызывает порт и проверяет отказ:
     - передача с непроверенными позициями;
     - решение без причины;
     - приёмка с расхождением без фото;
     - действие без прав;
     - повторная фиксация решения.
   - **Интерфейс.** Сквозной тест убеждается, что то же действие недоступно или отклонено
     с понятным текстом.

5. **Границы слоёв — правило ESLint.** Данные фикстур (`@/adapters/fixtures/data/*`) импортируют
   только `adapters/fixtures` и `adapters/demo`. Прежние запреты для экранов остаются. Нарушение —
   ошибка линтера, а линтер — шаг конвейера.

6. **Размер бандла — порог в `scripts/bundle-budget.json`.** Скрипт считает gzip всех JS-файлов
   клиента и самого большого из них. Порог — текущий размер плюс 10 %. Превышение роняет шаг.
   Порог поднимают осознанно, правкой файла с объяснением в коммите.

7. **Lighthouse — пороги задаются целью, а не замером.** Проверяются три экрана, профиль
   «десктоп». Пороги:
   - доступность — не ниже 0,95;
   - практики — не ниже 0,9;
   - производительность — не ниже 0,7.

   Если экран цель не проходит, это находка в `TASKS.md`, а не повод снизить порог.

8. **Конвейер.** `.github/workflows/ci.yml` на каждый пуш и запрос на слияние. Шаги по порядку:
   1. типы;
   2. линтер;
   3. тесты;
   4. проверка фикстур;
   5. сборка;
   6. размер бандла;
   7. сквозные тесты с консолью, EMBER и axe;
   8. Lighthouse.

   Падение любого шага роняет проверку. Тот же порядок повторяет `bun run ci` локально: он
   печатает код возврата каждого шага и завершается с ненулевым кодом при первом падении.

   Запрет слияния с упавшей проверкой включается в настройках репозитория: правило ветки `main`,
   «Require status checks to pass». Это настройка аккаунта владельца. Файл конвейера её
   не заменяет, и поставить её из кода нельзя.

## Последствия

- В `devDependencies` добавляются `@types/bun`, `@playwright/test`, `@axe-core/playwright`,
  `lighthouse`. Версии не моложе суток — по правилу `bunfig.toml`.
- Скрипты `.verify` остаются инструментом ручных проверок. Сквозные тесты в репозитории их
  не копируют, а закрепляют то, что должно проверяться всегда.

## Что не делаем

- Визуальное сравнение снимков экранов: пороги EMBER проверяются правилами, а не пикселями.
- Нагрузочные тесты и тесты адаптера PostgreSQL — это Q7.
