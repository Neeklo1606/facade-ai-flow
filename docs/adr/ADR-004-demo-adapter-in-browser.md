# ADR-004. Демо-адаптер работает в браузере, серверные функции — транспорт рабочего режима

- **Статус:** принято
- **Дата:** 2026-09-16
- **Уточняет:** [ADR-001](ADR-001-data-layer.md) (п. 3–4), [ADR-002](ADR-002-state-and-persistence.md) (п. 5–6)
- **Задачи:** P2-1, P2-6

## Контекст

ADR-001 направляет чтение и мутации через серверные функции TanStack Start поверх портов.
ADR-002 требует, чтобы демо-режим сохранял состояние в `sessionStorage`, продолжал симуляцию
после перезагрузки и сбрасывался кнопкой.

Приложение собирается Lovable под Cloudflare Workers (`nitro`, пресет `cloudflare-module`).
Если держать демо-состояние на сервере:

- память изолята не общая между запросами и исчезает при его выгрузке — сценарий показа
  рвётся в случайный момент;
- в одном изоляте состояние общее для всех зрителей — два человека, открывшие демо, видят действия друг друга;
- `sessionStorage` на сервере недоступен, а постоянное хранилище (KV, Durable Objects) —
  инфраструктура ради демо, которой в плане нет.

## Решение

1. **Один набор портов, два транспорта.** Экраны обращаются к `src/api/client.ts`; клиент вызывает
   либо демо-адаптер в браузере, либо серверные функции `src/api/functions.ts`. Методы и типы одинаковые.
2. **Источник выбирается переменной `VITE_DATA_SOURCE`:** `demo` (по умолчанию) или `server`.
   Сборка для показа и Lovable — `demo`. `server` — для разработки серверной части и с фазы 3 для PostgreSQL.
3. **Демо-адаптер (`src/adapters/demo`) живёт во вкладке:** состояние, «часы демо», симулятор событий,
   сохранение в `sessionStorage`, сброс. Таймеры допустимы только внутри него.
4. **Серверные функции проверяют вход и выход схемами контрактов** и подставляют сотрудника на сервере.
   Пока нет PostgreSQL, они работают поверх того же демо-адаптера в памяти сервера — этого достаточно,
   чтобы проверять транспорт, но не для показа.
5. **В демо маршруты рендерятся на клиенте** (`defaultSsr: false` в `src/start.ts`): сервер не знает
   состояние вкладки, а серверный скелетон и клиентские данные расходятся при гидратации — это проверено
   на первой версии, где сервер рендерил скелетон. Сервер отдаёт оболочку страницы, loader на сервере
   не загружает данные (`src/api/prefetch.ts`). В режиме `server` — полный SSR: loader загружает данные
   на сервере, и они передаются клиенту вместе с HTML.

## Последствия

**Плюсы**
- Показ клиенту не зависит от жизни изолята и не смешивает зрителей.
- Экраны не знают, откуда данные: переход на PostgreSQL — замена адаптера за серверными функциями.
- Серверные функции проверены уже сейчас, в режиме `server`.

**Минусы**
- В демо первый кадр после перезагрузки — оболочка и скелетон, а не готовые данные.
- Два пути в клиенте API (`demo`/`server`) нужно держать одинаковыми; расхождение ловят типы портов
  и проверка выхода схемами на сервере.

## Условия приёмки

- Экраны импортируют только `src/api`, не адаптеры и не порты (правило линтера из P1-7).
- `VITE_DATA_SOURCE=server` открывает те же экраны через серверные функции.
- В режиме `demo` сценарий показа выживает перезагрузку и не видит действий других вкладок.
